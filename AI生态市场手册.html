CHAPTER 01 · PART 1 · 生态与市场

Agent 生态全景：为什么现在是卖铲子的时间窗

淘金热里最稳的生意是卖铲子。这一章用可核实的数据回答三个问题：盘子有多大、窗口为什么是现在、个人开发者的位置在哪里。

📊

先把盘子看清楚：钱在流入，Agent 还在半山腰

难度 ★适合：零基础

先看最有分量的一组数。Menlo Ventures 的年度报告《2025: The State of Generative AI in the Enterprise》（基于对 495 名美国企业决策者的调查）统计：企业生成式 AI 支出在 2025 年达到 370 亿美元，是 2024 年 115 亿美元的 3.2 倍；其中编码类工具一项就占到部门级 AI 支出的 55%（约 40 亿美元），是所有品类里最大的一块。

但「在用 AI」和「真 Agent 化」是两回事：同一份报告把企业部署中只有 16%（创业公司 27%）归为「真 Agent」，其余大多是固定流程的自动化。采用率的其他口径也可以对照着看：麦肯锡 2026 年版 State of AI 调查显示，收入超过 10 亿美元的大型组织里有 40% 报告正在规模化部署 AI Agent（上一轮调查是 27%）；Grand View Research 则估算 AI Agent 市场规模 2026 年约 109 亿美元，预计 2033 年达到 1829 亿美元（年复合增速约 49.6%）。

把这两组数放在一起读：支出在翻着倍涨，而真正的 Agent 渗透率还不到两成——中间的落差，正是工具和服务的空档。

铲子经济学：个人开发者的位置在哪

难度 ★★适合：独立开发者 / 自动化从业者

平台大战的历史规律反复出现：平台之间抢用户、卷模型的时候，给所有平台供货的人赚稳定钱。这个窗口有三个特征，在 2026 年的 Agent 生态里同时成立：

  • 基础设施刚标准化：MCP 统一了「Agent 怎么连工具」，Agent Skills 统一了「Agent 怎么装知识」。协议和格式都定了，但上面跑的产品远没有饱和——这正是一代工具商的典型起点。
  • 买方习惯已经养成：76% 的 AI 用例外购、27% 的 AI 应用支出走产品自增长渠道（传统软件只有约 7%），意味着个人开发者不需要销售团队，把东西放进目录里就可能被买到。
  • 目录多、门槛低：官方 MCP Registry、PulseMCP（收录约 2.2 万个 server）、skills.sh（累计近 2.8 亿次安装）、Claude Code 插件市场、Cline 内置 Marketplace——分发渠道已经铺好，且大多免费上架。

个人开发者的三个现实位置：一是垂直 MCP server——把某个行业的 API、内部系统或数据源封装成标准工具，这是编码类支出占 55% 的直接映射；二是技能与知识包——把流程经验做成 SKILL.md 资产（第 04 章专门讲怎么做）；三是迁移与合规服务——协议换了传输方式、规范出了新版，企业的存量 server 需要有人帮着升级。

读这些数字时还要留意口径差：市场规模预测（109 亿、1829 亿美元）出自研究机构的模型估算，采用率（16%、40%）出自企业问卷，两者不能相乘得出「确定的蛋糕」。更稳妥的做法是盯结构性信号——编码类支出占比 55%、外购比例 76%，它们直接指向「现在就有人付钱买工具」的位置，而不是三年后的想象空间。

同样要记住窗口的另一半：Menlo 的数据里「真 Agent」只有 16%，说明大量采购仍在试点阶段。反方观点也要写进决策里：平台随时可能把热门工具做成第一方功能，标准的每次演进都会让存量工具产生维护成本。对冲方式是选「平台懒得做深」的位置——行业私有系统、本地合规环境、跨平台迁移这类脏活累活，恰好是大厂最不优先做的。卖铲子不承诺挖到金子——本手册所有收益讨论只给区间和口径，不构成任何收入承诺。

政策差异与各自的「品类气质」

难度 ★★★适合：正在选渠道的开发者

Claude Skills / 插件市场的气质是「工程化」。插件可以把技能、子代理、hooks、MCP server 打成一个单元安装，官方目录分官方、社区、第三方三层；市场还允许你在安装前查看插件占用的上下文成本。适合发布需要代码执行和工具调用的重流程资产。

skills.sh 的气质是「排行榜竞争」。安装量即排名，头部效应明显：榜首 find-skills（vercel-labs 官方）430 万次安装，第二名 grill-me 150 万，微软 azure-skills 合计 900 万、飞书 open.feishu.cn 技能包合计 1910 万（skills.sh 页面，检索 2026-11-08）。冷启动没有流量扶持，教程、README 和榜单话题就是你的分发渠道。

OpenAI 一侧要拆开看：Codex 插件系统 2026 年 3 月上线，InfoWorld 报道其定位是「帮助企业治理 AI 编码 Agent」，当时第三方市场尚未完全开放——这属于典型的早期窗口：给企业做连接器（Slack、Figma、Notion 类集成）竞争者还少。GPT Store 则相反，入口收缩、回报计划不再扩张，把新品优先放到别处更划算。

Cline 与 MCP 目录的气质是「管道」。Cline Marketplace 内置在编辑器里一键安装，官方文档反复强调安全：只装你信得过的 server、密钥放环境变量、谨慎使用 autoApprove。官方 MCP Registry 只是元数据目录而非包管理器，REST API 已在 2025-10-24 冻结在 v0.1，预览期不承诺数据持久性——适合当作「被发现的注册处」，真正的服务运行在你自己的域名上。

MCP 协议最小课：工具、资源与传输

不背规范，只讲能让你动手的那部分：三种角色、三种原语、两种传输、一次握手，外加一个官方示例 server 的逐行解剖和版本演进的避坑清单。

🔌

架构与三种原语：谁控制谁

难度 ★★适合：零基础

MCP 是一个开放协议，全部消息都是 JSON-RPC 2.0。三种角色：宿主应用（Host，比如 Claude Desktop、各家 IDE）内嵌一个或多个客户端（Client），每个客户端与一个服务器（Server）保持一对一连接；Server 负责提供上下文与能力。官方文档说这个设计参考了语言服务器协议（LSP）——编辑器生态当年靠 LSP 一次接入了所有语言，MCP 想对工具生态做同一件事。

Server 可以提供三种原语，区分它们最简单的记法是「谁控制」：Tools 工具是模型控制的——模型根据上下文自己决定何时调用；Resources 资源是应用控制的——宿主决定把哪些数据放进上下文；Prompts 提示是用户控制的——用户主动选择模板。客户端一侧也有对应特性：Elicitation，让 server 在执行中反向向用户请求信息。规范同时划了安全红线：工具的 annotations 描述必须视为不可信（除非来自可信 server），调用前应当有人工确认环节。

MCP 架构：一个 Host、多个 Client、多个 Server

一次完整调用在报文层面只有两步：客户端先发 tools/list 拿到工具清单（含 name、description、inputSchema），模型选中某个工具后，客户端再发 tools/call 携带参数执行。失败有两种形态要分清：请求本身有问题走 JSON-RPC 协议错误（如未知工具返回 -32602），业务失败——比如参数格式不对——则用结果里的 isError: true 返回；规范建议把后者交给模型自行修正重试。你的报错信息写得越「可执行」，模型自救的成功率越高。

💬 规范原文：tools 一章写道「Tools in MCP are designed to be model-controlled」，即模型可以基于对上下文的理解自动发现并调用工具；但同一节也警告，出于信任与安全，应当始终保留可以拒绝调用的人在水循环（human in the loop）里。

两种传输与一次握手

难度 ★★★适合：要动手写 server 的人

规范当前定义了两种标准传输，其余（如旧版 HTTP+SSE）已废弃：

维度stdioStreamable HTTP
进程形态客户端把 server 当子进程启动server 是独立进程，可服务多个客户端
消息通道stdin 读入 / stdout 写出，按行分隔单一 MCP endpoint，POST 发消息、GET 开 SSE 监听
日志纪律stdout 只准写 MCP 消息，日志必须走 stderrHTTP 响应之外可正常写 stdout
会话与版本进程即会话；版本由握手或每请求 _meta 声明Mcp-Session-Id 头 + MCP-Protocol-Version 头
适用场景本地、单用户、低延迟工具远程、共享、托管型服务

握手分两个时代，这是 2026 年最重要的版本变化：Legacy（2025-11-25 及更早）用 initialize 请求协商能力与版本，客户端再回一条 initialized 通知才进入正常工作；Modern（2026-07-28 起）取消了握手，每个请求自带 _meta 协议版本元数据，客户端可以先调 server/discover 探明服务器支持哪些版本，版本不被支持就收到 UnsupportedProtocolVersionError（错误码 -32022）并列出可用版本。旧版 HTTP+SSE 传输自 2025-03-26 版规范起被 Streamable HTTP 取代。

  • stdio 三条铁律：消息按行分隔且不得内嵌换行；server 不得向 stdout 写任何非 MCP 消息（print / console.log 会直接毁掉协议流）；stderr 随便用。
  • Streamable HTTP 安全三件事：校验所有连接的 Origin 头（防 DNS 重绑定）、本地运行只绑 127.0.0.1、给连接加认证——规范原文特别警告不做这三件事时，远程网页可以操纵你本地的 MCP server。
  • 版本兼容：支持 2026-07-28 的双时代（dual-era）服务器，stdio 上可以先用 server/discover 探测、失败再回退到 initialize。

Skills 与提示词资产：从提示词到可复用资产

一个 SKILL.md 文件加一个文件夹，就是 2026 年门槛最低的数字资产。这一章讲清格式与加载机制、三种产品化路线，以及哪些提示词值得卖、哪些白送都嫌占地方。

SKILL.md：一个文件夹的生意

难度 ★★适合：零基础

Agent Skills 的官方定义很朴素：一个文件夹，里面必须有 SKILL.md，可以附带 scripts/（可执行脚本）、references/（参考资料）、assets/（模板资源）。SKILL.md 分两段：YAML frontmatter 写元数据（开放标准最低要求 name 和 description），正文写给 Agent 看的操作指令。Anthropic 工程博客把这个结构比作「给新员工的入职指南」——平时放着，遇到对应任务再翻开。

产品化三条路：提示词包、风格包、知识包

难度 ★★★适合：会写文档的开发者

提示词包是最直接的迁移：把你验证过的 SOP（代码审查清单、发布流程、事故排查）从聊天记录里搬进 SKILL.md，正文写「步骤 + 判断标准」，把长参考资料挪进 references/。判断搬迁是否成功的标准很简单：换一个没上下文的新会话，Agent 照样能按步执行。

风格包有官方样板可抄：anthropics/skills 里的 frontend-design 在 skills.sh 上有 110 万次安装，证明「把设计审美写成可执行约束」是刚需。同类可做的还有团队写作风格、数据可视化规范、品牌合规检查——共同点是输出可以被一眼评判好坏。

知识包的天花板最高：行业规则、内部系统说明书、监管流程，配上校验脚本就是「会自动执行的公司知识库」。这条路线天然面向企业客户——他们要的不是文件本身，而是知识的一致交付，价格也按服务谈而不是按份卖。

资产管理上，把散落提示词变成资产只差四步：统一命名（小写连字符，见 agentskills.io 规范）、Git 仓库管版本（license 字段写清授权）、写好 description 当货架文案、按第 02 章的决策表分发。另外，MCP 社区工作组在推进 Skills over MCP 扩展，技能未来可以直接经 MCP 分发——仓库结构今天就按标准建，后面只是换个货架。

写 frontmatter 有两个产品化细节：官方文档明确「只有 description 是推荐字段，Agent 靠它判断什么时候用这个技能」，description 加上 when_to_use 的触发补充，会在技能列表里合计截断到 1,536 字符——前 50 个字最值钱。allowed-tools 则是信任开关：它让技能在被调用的那一轮免确认使用列出的工具，轮次结束即失效；列得越少越可信，也越容易被企业客户放行。

Loop 与 Graph：Agent 框架里的产品形态

同一个「让 AI 自动干活」，可以是一次 API 调用、一个循环，或一张图。选对产品形态，交付成本就赢在起跑线；选错形态，复杂度会吞掉全部利润。

🧭

三种形态，一图分清

难度 ★★适合：零基础

Anthropic 在《Building Effective Agents》（2024-12-19 发布）里给出的定义被业内广泛引用：workflow 是「LLM 和工具按预先定义好的代码路径编排」出来的系统；agent 则是「LLM 动态决定自己的流程与工具使用」的系统。前者像流水线，后者像一个自己决定下一步怎么走的员工。落到可售卖的产品上，常见形态有三种：

  • ① 一次调用：分类、摘要、改写、信息抽取——答案一步就能出。Anthropic 的原话是：对很多应用，「优化单次 LLM 调用（配合检索与上下文示例）通常就够了」。如果你的卖点是稳定和便宜，别把它复杂化。
  • ② Agentic Loop（循环）：模型决策 → 调用工具 → 结果回填 → 再决策，循环到判定任务完成。适合步数不可预知的活：深度调研、代码调试、批量修复、多源交叉核对。循环次数即成本，务必设上限。
  • ③ Graph（图编排）：把流程画成节点加边，LLM 节点与确定性代码节点混排，支持分支、并行、人工审批、断点恢复。LangGraph 官方定位就是「面向长时间运行、有状态 agent 的低层编排框架与运行时」，核心能力是持久化、人在回路、记忆与流式输出。

判断顺序建议从简到繁（Anthropic 的核心建议就是「找最简单的可行方案」）：先问一次调用能不能过；不能，再问步骤能不能预先画出来——能，就用 workflow/graph；只有连步骤数量本身都不可预知时，才值得为 loop 的不确定成本买单。

三个常见误区：一是把 loop 当默认形态——每轮循环都是真金白银的 token，需求其实一步能解时，循环只是烧钱；二是把 graph 画成蜘蛛网——节点越多、分支越密，半年后连你自己都改不动；三是过早绑定框架——Anthropic 明确建议先用裸 API 跑通最小流程，确认需求真实存在，再决定要不要引入 LangGraph 这类编排层。

选形态自查清单

难度 ★适合：动手前过一遍
  • 任务答案能否一步给出？能 → 一次调用，别搭框架。
  • 步骤可否预先枚举、且中途需要人拍板？是 → graph/workflow，把审批节点画进图里。
  • 需要尝试的步数本身不确定（搜多少页、改几轮代码）？是 → agentic loop，并设最大轮数与预算熔断。
  • 客户要的是「结果」还是「可维护的流程」？要结果 → 你按效果收费；要流程 → 你按交付物与维护费收费。
  • 框架迁移成本评估过吗？工作流逻辑尽量写在图/流程定义里而不是散落在代码里，换框架时才是搬家而不是重建。
  • 需求真伪验证过吗？先用「人肉 + 一次调用」把活干三天，确认客户真会为它省钱，再固化成工作流——顺序反了就是给自己造玩具。
  • 每次执行的 token 消耗与耗时记录了吗？没有这份账，报价就是拍脑袋，loop 类项目尤其如此。

最后一条选型建议：团队只会低代码，就从 n8n、Dify 起步；会写代码，LangGraph、裸 API 更灵活。选型跟着团队现有技能走，比跟着流行走省得多——迁移成本永远比学习成本贵。

变现模式四型：计量、订阅、授权与托管

同一个能力，可以用四种姿势收钱。模式决定了你的现金流形状、成本结构甚至退款纠纷数量——它比选什么技术栈更重要。

📐

四型各是什么

难度 ★★适合：零基础
  • 计量（usage-based）：按 token、次数或事件收费，成本随用量走。API 生态的默认形态——Claude API 按百万 token 计价，例如 Sonnet 档输入 $3、输出 $15（检索 2026-11-08；官方定价页在部分地区无法直接访问，数字以当期官方页为准）。适合成本与用量强相关的产品；坏处是客户账单不可预测，容易劝退谨慎的买家。
  • 订阅（subscription）：按月/年固定价。个人与开发者工具的默认形态：GitHub Copilot Pro $10/月（含 300 次 premium requests）、Cursor Pro $20/月、Supabase Pro $25/月/组织（检索 2026-11-08）。现金流可预测，是独立开发者的主力模式。
  • 授权（license）：一次性或按年买断使用权。开源项目的商业版、企业内网私有化部署、白标授权都属此类。n8n 的 Sustainable Use License 是典型设计：自用与咨询服务免费，转售/白标/SaaS 化平台本身需另签商业协议——「卖使用权」的边界写在许可证里。
  • 托管（hosted/managed）：替客户跑起来、保可用性，收月费加用量。Supabase 把「Postgres+鉴权+存储」托管成 $25/月起步；个人卖家的「部署+运维+培训」打包年费也归这里。托管卖的是省心，定价里要计入你的运维时间。

落地细节决定成败：计量单位要选客户看得懂的——对非技术客户按「次」「文件数」计价，token 只对开发者透明；订阅阶梯至少做三档（免费体验、个人主力、团队协作），让升级路径自然发生；授权谈判的通行结构是「初始买断 + 年度维护费」，后者才是长期现金流的来源。

收款基础设施：计量、MoR 与托管底座

难度 ★★★适合：准备上线的人

收钱远不止放一个支付按钮，至少要接好三块：

  • 计量与账单：Stripe Billing 的用量计费按账单额抽 0.7%（随用随付口径，不含一次性账单），基础用量计费通过 Meters API 提供；更大规模用 Stripe 旗下 Metronome（检索 2026-11-08，页面以港元区显示，具体以你所在区为准）。
  • 商户记录方（MoR）：个人卖家跨境收款的捷径。Lemon Squeezy 官方费率 5% + $0.50/笔、无月费，由它作为商户记录方替你处理全球税务与合规；第三方对比称 Paddle 同为 5% + $0.50（以两家官网当期为准）。MoR 比裸 Stripe 贵，但省下逐国税务登记的真金白银与时间。
  • 托管底座：Supabase Pro $25/月/组织起，含 $10/月算力额度，超出后按用量计（如 $0.00325/MAU）；Pro 档默认开启用量封顶（spend cap），防隔夜天价账单——给客户部署服务时优先选有封顶的供应商。
  • 发票、退款与税务：个人卖家最容易低估的隐性工作。MoR 模式的核心价值之一就是替你开发票、处理退款与全球税务；走裸 Stripe 则这些都要自己来。起步期先用支付平台托管的最小方案（支付链接 + 订阅开关），计量逻辑先做在自己产品里，跑通了再上专业计量服务。

选模式的三问决策框架

难度 ★★适合：定价前过一遍
  • 成本是否随客户用量线性上涨？是 → 计量，或「订阅 + 计量上限」，把变动成本转嫁出去；否则你每多一个重度用户就多亏一笔。
  • 客户是个人还是企业？个人看齐 $10-20/月心理价位；企业按席位加授权谈，能接受一次性买断与私有化部署（企业采购逻辑见第 07 章）。
  • 你有没有精力做运维与合规？没有 → MoR 代收代缴 + 托管底座 + 托管型交付，把时间花在产品；有 → 授权与私有化部署的毛利更厚。
  • 定价页怎么写？给区间和锚点：主推档放中间，高价档承担「锚定」职责；标明「不含税」「按年付优惠」；价格注明更新日期——这既是诚实，也减少纠纷。

合规提醒：本章所有价格均为检索日（2026-11-08）的公开口径，各家政策随时调整，签约前以官网当期为准；封装第三方服务（支付、托管、模型 API）时遵守其服务条款，不要为规避费率或配额设计套利方案。本文不构成投资建议，也不承诺任何收入水平。

从 0 到第一笔收入的上线清单

难度 ★★适合：首次收费
  • 开户：个人跨境收款优先 MoR（见上），国内客户再补一套本地支付；账户信息与收款主体一致，避免后续提现卡壳。
  • 定价页：三档结构，注明币种、是否含税、扣款周期与退订入口——订阅模式下，退订越透明，投诉越少。
  • 计量埋点：哪怕先只记「次数」，也要从第一天记——计费争议的仲裁依据就是你的用量日志。
  • 失败重试与催缴：卡扣失败是订阅流失的主因之一，支付平台自带的智能重试与催缴邮件默认打开（Stripe Billing 已内置这两项）。
  • 对账看板：每周看一次订阅收入、活跃用量与退款率；数字不看的定价，改不动。

企业采购的隐形门槛

难度 ★★★★适合：想接企业单的人

企业的钱最厚，门也最重。安全评审的通行证通常是 SOC 2 Type II 报告——它证明的不是「你有安全政策」，而是「控制措施在一段观察期内持续有效」，企业采购、安全评审与合规岗都拿它当基线。AI 类工具还要多过一层审：训练数据是否用了客户数据、上游 LLM 供应商（子处理者）是谁、有没有对齐 NIST AI RMF / ISO 42001 的治理框架。

  • 给个人卖家的现实策略：先卖开发者与个人（今天就能收钱），企业单先通过平台、代理商或老客户的部门级试点承接；等有了企业案例、能提供安全材料与数据处理协议后，再直营大单。
  • 把流程拆成六步准备材料：需求部门提单 → 安全问卷 → SOC 2 报告与渗透测试摘要 → 数据处理协议 → POC 验证 → 采购签约。前四步的材料都可以在没客户时提前备好；等单子来了再准备，周期至少翻倍。
  • 私有化部署 + 授权往往是个人卖家进入企业的最短路径：客户的数据不出内网，安全评审好过，你也顺势从「卖软件」升级为「卖部署与维护」（定价方式见第 06 章授权与托管两型）。
  • 读懂「谁签字」：使用部门要的是效果，IT/安全要的是风险闭环，采购与法务要的是合规凭证——你的销售材料要按这三种人各准备一版。

第一个 MCP 服务器：用 AI 编程两小时做出来

MCP 是 AI 应用连接外部系统的开放标准。这一章带你用 AI 编程助手结对，从空文件夹做到「能被 Claude Desktop 调用」的最小服务器，全程约两小时。

🧭

十分钟搞懂 MCP

难度 ★适合：零基础

官方文档把 MCP 比作「AI 应用的 USB-C 接口」：一个开放标准，让 Claude、ChatGPT、VS Code、Cursor 等客户端都能用同一种方式连接外部数据、工具与工作流——你的服务器做一次，所有支持 MCP 的客户端都能接。一个 MCP 服务器可以提供三类能力：Resources（可读的类文件数据）、Tools（LLM 经用户批准后调用的函数）、Prompts（预设任务模板）。新手只需要从 Tools 入手。

  • 传输方式两种起步：stdio（本地子进程，标准输入输出通信，调试最简单）与 Streamable HTTP（远程部署用）。第一个服务器选 stdio。
  • 官方 SDK 覆盖很全：TypeScript、Python、Go、Java/Kotlin、C#、Ruby、Rust 都有官方或示例支持。新手二选一：TypeScript（npm 生态）或 Python（uv + mcp[cli]）。
  • 先想清楚给谁用：翻一遍官方示例服务器仓库（filesystem、fetch 等），你会看到好服务器的样子——工具少、描述准、权限小。
  • 选题三条标准：数据或接口你有权访问（不碰登录后内容、不绕过授权）；每周至少用三次（高频才值得做成工具）；调用出错可回退（第一题不做不可逆的写操作）。
💬 一线声音：MCP 官方文档原话：MCP「provides a standardized way to connect AI applications to external systems」，如同「USB-C port for AI applications」——接口标准化之后，生态里的每个客户端都是你的潜在分发渠道。（来源：modelcontextprotocol.io，检索 2026-11-08）

把服务包成工具：API 封装、鉴权与错误处理

你手上的 API、脚本和数据服务，封装成 MCP 工具之后就成为 AI 生态里人人可调用的「铲子」。这一章只讲可核实的东西：字段怎么定义、密钥放哪里、错误怎么返回、条款边界在哪，每一条都给规范原文或官方页面。

🧰

封装模式：从「枚举端点」到「面向任务」

难度 ★★适合：会一点编程

MCP（Model Context Protocol）规范里，一个工具由 name、title、description、inputSchema、outputSchema、annotations 六类字段描述：inputSchema 是 JSON Schema，声明模型该传什么参数；outputSchema 描述结构化返回，客户端可以照它校验 structuredContent。规范还建议：即使返回结构化内容，也同时把序列化 JSON 放进一个 text 块，向后兼容旧客户端。工具名建议 1–128 个字符，只用字母、数字、下划线、连字符和点。

最常见的失败姿势是把 REST 端点一对一机械映射成工具。Stainless 与 Scalekit 两家做 API 封装的实践复盘都指向同一件事：模型不需要 30 个「端点」，它需要 5 个「任务」——把「查订单状态」「创建退款单」各做成一个工具，在工具内部再去调用多个端点、拼好数据。description 不是摆设：模型靠它决定什么时候调用你的工具，把参数含义、单位、限制写清楚，调用准确率立竿见影。

  • 每个工具对应一个用户任务，而不是一个 HTTP 路由；输入参数用扁平结构，少嵌套。
  • 返回结果控制体积：列表默认分页，大字段给摘要，详细数据用 resource_link 让客户端按需取。
  • 规范要求服务器声明 tools 能力时，工具集合「不得随连接或其它请求变化」，可随授权范围变化——同一工具对不同权限用户返回不同结果集是允许的。
💬 规范原文：MCP 规范在 Tools 一节警告：为了信任与安全，「should always be a human in the loop with the ability to deny tool invocations」——客户端应向用户展示哪些工具暴露给了模型，并在敏感操作时弹确认。这意味着你封装的工具越有用，越要在 description 里写明副作用，别让模型「静默」干大事。（来源：modelcontextprotocol.io Tools 规范）
🔑

鉴权与密钥管理：一条铁律，两条路线

难度 ★★★适合：要上线的产品

铁律只有一条：密钥永不进代码。OWASP《Secrets Management Cheat Sheet》把「不在源码中硬编码 API key」列为第一原则，配套要求密钥轮换与最小权限访问控制。落地动作：.env 文件不进 git、CI/CD 用平台的 secret 注入、密钥走系统级密钥管理器而非聊天窗口。

MCP 规范按传输方式给了两条路线：stdio 本地传输被明确建议不走 OAuth 流程，「从环境变量获取凭据」即可——本机场景环境变量就是正解。HTTP 远程传输则 SHOULD 遵循规范的授权机制：MCP 服务器扮演 OAuth 2.1 的「资源服务器」，授权服务器负责签发 access token。规范里连串 MUST 值得逐条对照实现：客户端必须实现 PKCE 防授权码拦截；服务器必须实现 RFC 9728 受保护资源元数据并在返回 401 时用 WWW-Authenticate 头指路；令牌请求必须带 RFC 8707 的 resource 参数；服务器必须校验 token 的 audience 是自己，禁止把客户端的 token 原样透传给上游 API（token passthrough 被点名禁止，这正是「混淆代理人」攻击的入口）。

  • 多用户产品给每个用户单独走一次 OAuth 授权，绝不用一个全站共享的 API key 顶替所有用户的身份。
  • 规范还警告：不要把密码、API key、PII 等敏感参数标记成 x-mcp-header——它们会被镜像进 HTTP 头，对网络中间设备可见。
  • 授权服务器应发短时 token；对公共客户端必须做 refresh token 轮换。这些不是加分项，是规范原文。
⏱️

错误处理与超时：让模型能「自纠」

难度 ★★适合：零基础起步

MCP 把错误分成两类，处理方式完全不同。协议错误走 JSON-RPC error（例如未知工具返回 -32602），这类错误模型很难自行修复；工具执行错误则放在正常结果里、置 isError: true，附上「可行动」的文字——规范给的例子是「离港日期无效：必须是未来日期，当前日期是 08/08/2025」。后者的意义在于模型读得懂、能自己改参数重试。你的封装层应该把上游 API 的 4xx/5xx 翻译成这种人类可读、可执行的提示，而不是把堆栈原样吐给模型。

超时方面，规范把「为工具调用实现超时」列为客户端 SHOULD；作为封装者你要反过来做：对上游 REST 调用自己设超时、用指数退避重试 429/5xx，别让调用方的网关随机掐断。超过十几秒的长任务别硬等——规范 Stateful Tools 一节给了标准答案：创建类工具返回一个不透明句柄（如 bsk_a1b2c3），后续调用带着句柄查询进度；句柄要校验授权、声明生命周期，访问过期句柄时返回工具执行错误提示模型重建。

  • 服务端安全四条 MUST：校验所有输入、实现访问控制、对调用限速、消毒输出——规范原文，逐条落进代码。
  • 句柄背后如有状态，把保留策略写进创建工具的 description（例如「24 小时未使用即过期」），模型看得见才能规划。
⚖️

条款边界与分发：封装别人的服务之前

难度 ★适合：所有人

封装第三方服务有一条不能踩的线：只走对方官方 API 与其服务条款允许的授权方式。不封装「爬登录后内容」的能力，不做绕过配额、共享账号、规避付费墙的工具——这些既违反平台条款，也会让你的产品随时归零。正确姿势是：核对目标服务的 API 条款与速率限制，把额度策略写进工具 description，在限速时返回友好提示。

做好的工具往哪发？MCP 项目在 2025 年 9 月 8 日上线了官方注册表 registry.modelcontextprotocol.io（预览版），后端开源在 GitHub，相当于 MCP 服务器的「应用商店」索引；发布前把自己的服务条款、鉴权方式、数据用途在描述里写清楚，既方便用户也保护你自己。

💬 一线声音：Scalekit 在复盘「该不该给现有 API 套 MCP 壳」时强调，封装层的核心工作之一是把上游错误变成「清晰、可行动」的信息再交给模型，同时补上访问控制——这两点决定了工具在真实 agent 里的可用性。（来源：scalekit.com 博客，2026-11-08 检索）

一个技能（Skill）就是一个文件夹加一份 SKILL.md：门槛低到人人能写，但「有人愿意装」靠的是选题和写法。本章从 Agent Skills 开放标准、Claude Code 官方文档与 skills.sh 实时榜单出发，把选题、结构、边界声明和迭代讲透。

🎯

选题：从你自己的重复劳动里挖

难度 ★适合：零基础

Agent Skills 是一套开放格式：一个文件夹，核心是 SKILL.md（至少含 name、description 两个元数据字段加正文指令），旁边可带 scripts（可执行代码）、references（参考文档）、assets（模板资源）。这套格式由 Anthropic 率先发布为开放标准，2025 年 10 月 16 日 Anthropic 以研究文《Equipping agents for the real world with Agent Skills》正式介绍，如今已有包括 OpenAI Codex（2025 年 12 月 15 日起实验性支持）在内的多家 agent 产品采纳。

它的工作机制叫渐进式披露，分三阶段：启动时只载入每个技能的 name 和 description（Discovery）；任务匹配描述时才读入全文指令（Activation）；需要时才执行脚本或加载参考文件（Execution）。这决定了选题逻辑：description 是你唯一的「广告位」，而选题要选那种「一周内在你工作里出现三次以上、有明确输入输出、别人也搜得到关键词」的重复劳动——比如固定格式的周报汇总、特定平台的发布检查清单、某类发票的整理流程。太通用的选题（「写好代码」）挤不进任何描述匹配，太私人的选题（「我家路由器重启步骤」）没人装。

拿一对例子对齐感觉：「每次发布网站前逐项检查 SEO 标签并出报告」是好选题——输入（URL）、输出（检查清单结果）、触发时机（发布前）都写得出来；「帮我优化博客」是坏选题——没有边界，模型每次的理解都不一样。再往前一步：把检查清单写成十条明确规则放进技能，再配一个自动抓取页面标签的脚本，它就从「一段提示词」升级成了「一条可复用的流程」——这正是渐进式披露里 Execution 阶段的价值。

💬 官方口径：Anthropic 在上述研究文里把 Skills 定位为「给智能体装上现实世界所需能力」的机制，并专门讨论了恶意技能带来的安全风险——写技能本质是在分发一种「信任」：装你技能的人，等于把一段指令授权进了他们的 agent。（来源：anthropic.com 研究文，2025-10-16）

结构与文档写法：把预算花在 description 上

难度 ★★适合：会写 Markdown

官方文档给出的目录骨架是：SKILL.md（必须）＋ 按需的 reference.md、examples.md、scripts/helper.py——注意脚本是「被执行」而不是「被读入上下文」。Claude Code 文档建议 SKILL.md 控制在 500 行以内；并且「description + when_to_use 合计文本在技能列表中于 1,536 字符处截断」——这段预算就是别人决定装不装你的全部依据，要写清「做什么 + 什么时候用 + 输入输出是什么」。

存放位置决定作用范围：个人级放 ~/.claude/skills/<名称>/（你的所有项目可用），项目级放 .claude/skills/（随仓库提交分享给团队），插件则放在插件目录的 skills/ 下并以「插件名:技能名」调用。目录名或 frontmatter 的 name 会直接成为你可以敲的斜杠命令（/技能名），所以命名用小写连字符、见名知义，别起「my-skill-v2-final」这种名字。要特别留意：走平台上传/打包分发时，frontmatter 只允许六个键——name、description、license、compatibility、metadata、allowed-tools——多写一个键会在打包时报硬错误；其余丰富字段（when_to_use、argument-hint、context 等）是 Claude Code 的本地扩展，不是标准的一部分。

  • 正文三段式：何时使用 / 分步操作 / 边界与失败处理，每步给可复制的命令或模板。
  • 给一个最小可跑示例：宁可 20 行能跑通，不要 200 行「看起来全」。
  • description 怎么花掉 1,536 字符预算？照这个骨架写：「用于……场景。当用户要求……或……时使用。输入需要……。输出为……。不要用于……。」——触发词、输入输出、禁区一次写全。
  • 大技能拆「入口 + 参考」：入口 SKILL.md 保持百行内，细节放 reference 文件按需读，省上下文也方便维护。
  • allowed-tools 可以在该技能被调用的当轮预授权工具白名单——涉及写操作时用它收权，而不是放开全部权限。

示例、边界声明与版本迭代

难度 ★★适合：准备发布的人

「边界声明」是新手技能和可靠技能的分水岭。写明三件事：这个技能不做什么（例如「不处理含个人身份信息的文件」）、输入不满足时怎么降级（找不到文件时提示用户而不是瞎猜）、脚本失败时的提示语。这些既是质量，也是自保：Anthropic 官方都在研究文里提醒恶意技能风险，一个把边界写清楚、脚本可审计的技能才值得被陌生人安装。

迭代用最朴素的工程方法：Git 管理源文件夹，语义化版本号 + CHANGELOG，每条变更注明要求的客户端版本（Claude Code 文档里多处功能标注了最低版本号，例如 claude.ai 同步技能需要 v2.1.228+——把你的依赖版本写进 compatibility 或说明里）。发布有三个台阶：先发 GitHub 仓库并给官方示例库 anthropics/skills 提 PR 换背书；再提交到 skills.sh 这类开放目录被 npx skills add 安装；最后可自建 Claude Code 插件市场（官方文档支持用 marketplace.json 建自己的目录）做自有分发。

发布前自检三问：换一个全新会话，只读 description 能否判断「什么时候该用它」；手动把脚本跑进失败分支，报错信息能否告诉使用者下一步怎么办；仓库里有没有 LICENSE 和 CHANGELOG，别人引用与 fork 是否有据可依。三问都过，再提交榜单——开放目录的安装量是公开计数，低质量技能的差评同样公开。

工作流模板产品化：n8n、Dify 模板的买卖

自动化平台把「流程」变成了可复制的资产：你搭一次，别人导入就能用。本章把 n8n 与 Dify 两个主流模板生态的现状、官方分成口径、打包方法与许可证边界一次讲清，所有数字标注检索日期（2026-11-08），以各平台当期政策为准。

🏪

市场现状与分成口径：先看官方页面怎么说

难度 ★适合：所有人

体量先看官方数字：n8n 模板库首页标注「14,004 Workflow Automation Templates」，分类覆盖 AI、Sales、IT Ops、Marketing、Document Ops（n8n.io/workflows，2026-11-08 检索）。官方创作者计划（n8n.io/creators）提供的是身份与曝光资源：Verified Creator 徽章、创作者目录收录、私有 Discord 频道、产品团队直连——页面未承诺任何按模板下载量的直接付费。官方写明的变现通道是联盟计划：n8n.io/affiliates 页面原文为「Receive 30% on all your referrals for 12 months」，即 n8n Cloud 订阅推荐佣金 30%、持续首年 12 个月，仅限 Cloud（Starter/Pro）订阅，PayPal 月结、余额满 100 欧元起付。

Dify 侧，Marketplace（marketplace.dify.ai）是插件与模板的官方目录，页面同时挂着 Dify Partners（伙伴验证）与 Creator Center（creators.dify.ai）入口。模板上架的官方路径在 Dify 文档里写得很清楚：应用内 Publish → Publish Update → Publish to Marketplace，或经 Creator Center 提交；插件则要打包成 .difypkg 并接受评审。给开发者的含义：这两家的「模板生意」目前都是你自己定价销售 + 平台给你分发与身份背书的模式，官方不按模板付费——收入预期请以自营渠道为主来规划。

头部量级也有参照：n8n 官方创作者目录页面展示的头部创作者，名下模板数在数百个量级（页面可见 394、380、361 个模板的账号样本，2026-11-08 检索）。对个人卖家的启示不是铺量，而是先做深一个垂直场景——用 10–50 个互相呼应的高质量模板建立「这个领域找你」的心智，比两百个互不相关的泛用模板更接近可持续的生意。

💬 社区口径：「能不能卖 n8n 模板」在社区长期被讨论。n8n 社区论坛的相关帖子里，被广泛接受的口径是：卖模板、用模板给客户做实施都是允许的，限制的是把 n8n 软件本身当作主要价值转售；官方未发布逐字声明，商用规模化前以许可证页与官方确认为准。（来源：community.n8n.io 相关讨论与 docs.n8n.io 许可证页，2026-11-08 检索）

打包法：把流程做成「导入即可用」

难度 ★★★适合：自动化从业者

两个平台的交付物不同：n8n 的模板 = workflow JSON + 搭建说明，官方文档把「用模板」与「分享模板」都收在 docs.n8n.io 的模板章节里；Dify 的模板 = DSL 文件——应用导出得到 .yml（DSL）或 .ifpkg 应用包，买家在工作室「创建应用 → 导入 DSL 文件」即可复现（docs.dify.ai 导入导出文档）。开源社区已经验证了这条路：awesome-dify-workflow 仓库收录了 75 个可直接导入的 DSL 工作流。

打包清单（每一条都来自买家投诉的高频坑）：

  • 脱敏：导出前删净自己的凭据、内部 URL、测试数据——模板里出现真实密钥是最严重的事故。
  • 配置面收敛：模型名、知识库 ID、webhook 地址、日期范围等全部抽成占位符，集中在工作流开头的「从这里开始」节点或环境变量集合。
  • 最小可运行版：先给一条能跑通的主链路，进阶分支作为可选模块，别让买家的第一次运行就被十几个未配置节点劝退。
  • 版本与变更记录：模板版本号 + CHANGELOG 写清适配的平台版本（Dify 旧版本导出的 DSL 存在兼容性问题，社区早有复盘）。
⚙️

配置化与文档：买家 10 分钟跑通

难度 ★★适合：零基础起步

模板和代码产品一样，文档就是产品。一套可复用的 README 骨架：适用场景与不适用场景（防止买家期望错位）、前置清单（需要哪些账号、哪些 API 额度、预计费用量级——费用只给区间并注明是你的估算）、五步安装（导入 → 配凭据 → 填占位符 → 试运行 → 激活调度）、逐节点参数说明、常见报错对照表、已知边界（哪些环节依赖平台版本、哪些接口可能变动）。

测试方法照搬软件行业：用一个干净账号从零走一遍完整安装流程，计时并记录卡点；每个占位符都要验证「填错时给出的报错能不能引导用户自己修好」。做不到这点的模板，差评会直接写在评论区。

定价与交付给一个不承诺收入的方法框架：按「买家省下的时间 × 该时间在买家行业的小时成本」估价值区间，再对照同类模板的公开标价带定锚；首发价可以低一些换首批评价，随版本迭代分阶段提价。商品页写清「一次购买含哪些后续小版本更新、平台大版本升级是否另计」——模板生意的售后纠纷大多出在这句话没写。

形态取舍与合规边界

难度 ★★适合：规划产品线的人

模板、MCP 工具、Skills 是三种形态，别硬凑一个：流程编排类需求（跨 SaaS 的自动化）适合做模板；「给 agent 补连接能力」适合做 MCP 工具；「把程序性知识装进 agent」适合做 Skill。判断标准是买家拿到手的第一动作：导入流程 → 模板；配置连接 → MCP；安装进 agent → Skill。

合规边界两条：其一，n8n 采用 Sustainable Use License，限制的是把 n8n 本身或其能力作为主要价值出售（如托管转售），为客户搭建工作流并收取实施费被明确允许，卖模板属社区共识地带，规模化前请以许可证页为准；其二，模板若封装了第三方服务（爬虫类需求尤其危险），必须遵守那些服务的条款——这条和第 09 章的封装边界完全一致。收益方面本手册不承诺任何收入水平：卖多少取决于你的分发渠道与定价，官方数字只有 30% 首年联盟佣金这一条口径（检索 2026-11-08）。

最后一个容易被低估的成本：跟平台版本。n8n 与 Dify 都在快速迭代，旧 DSL 与改名节点会失效，社区仓库里已有旧版 DSL 导入失败的复盘。把「已适配到平台 X 版本」写进商品页，既是对买家的预期管理，也是你售后排期表的第一行。

Graph 编排实战：用 LangGraph 类框架做多步骤产品

单轮对话做不成产品，多步骤、可恢复、有人工把关的流程才收得了费。本章以 LangGraph 为例讲清节点与状态的结构设计、中断恢复的官方姿势、评测方法，以及怎么把整个 Graph 打包卖出去。GitHub 仓库数据与 API 细节均注明检索日期（2026-11-08）。

🧠

结构设计：节点、状态、回环

难度 ★★★适合：会 Python/JS

LangGraph 自我定位是「低层编排框架」，专门面向长时运行、有状态的应用；官方 Graph API 文档把模型压到三个词：State 是所有节点共享的数据；Node 是读写这个状态的函数；Edge（含条件边）决定下一步走哪。动态控制流交给 Send 与 Command。仓库 langchain-ai/langgraph 的自述只有三个词「Build resilient agents」，MIT 许可，44,641 stars / 7,692 forks（GitHub API，2026-11-08 检索）——它是当下最主流的代码级编排选择之一。

  • 每个节点只做一件事，能独立测试；「抓取上下文」「分类」「起草」「审核」各自成节点，而不是一个 500 行大函数。
  • State 里只放「后续决策要用的依据」（工单 ID、分类结果、审核结论），原始大文件放外部存储、state 里存引用。
  • 条件边的分支名用业务词（needs_review、auto_reply），日志里人能读懂，评测时也好统计。
  • 回环是 Graph 的价值所在：改写不过审就退回重写，次数上限写进状态字段，避免无限循环烧钱。

动手顺序建议「先画后写」：把流程画成框图——哪些节点、哪些条件边、哪里回环、哪里需要人工——给每条边标注触发条件，再列一份状态字段清单。这张图既是开发蓝图，也是日后卖给买家时的文档素材。官方 overview 把 LangGraph 定位给「长时运行、有状态」的场景：如果你的流程一次跑完、从不需要恢复与回环，用简单的链式调用反而更省——不为用框架而用框架。

⏸️

人机交互点：interrupt() 与恢复的官方姿势

难度 ★★★★适合：要做生产的人

LangGraph 官方文档给出的中断机制：interrupt() 可以在任意节点内部调用，传入任何 JSON 可序列化的值抛给调用方；前提是编译图时配置了 checkpointer（生产环境用数据库等持久化实现）并在运行配置里给 thread_id。调用后图在原地挂起、状态经 checkpointer 存档，「无限期等待」恢复。恢复方式：用同一个 thread_id 重新 invoke，传入 Command(resume=...)——resume 的值会成为节点内那次 interrupt() 调用的返回值；可以配 response_schema（Pydantic 模型等）让传入数据自动校验。文档特别强调：Command(resume=...) 是唯一设计为作为输入传给 invoke/stream 的 Command 用法。

官方文档用加粗警告标出的三个坑，每一个都值得抄进你的代码评审清单：其一，恢复时运行时会「把整个节点从头重新执行」——interrupt() 之前的副作用（如新建审计记录）会被重复执行，必须幂等（用 upsert），或把副作用放到 interrupt 之后、隔离进独立节点；其二，不要用裸 try/except 把 interrupt() 包起来——你会吞掉运行时用来实现暂停的内部异常；其三，节点内多次 interrupt() 的调用顺序必须确定，恢复是「严格按索引匹配」的，条件跳过或循环里的 interrupt 会错位。

💬 产品视角：interrupt() 不是工程炫技，它就是付费点——「发送前人工审核」「下单前人工确认」这类环节，恰好是企业客户愿意为可控性买单的地方，也是你把 Graph 做成产品时的核心卖点。（结合 LangGraph 官方对 human-in-the-loop 场景的定位整理，来源见文末）
🧪

评测与调试：把评测集当回归测试

难度 ★★适合：所有人

官方 LangSmith 文档把评测拆成一条概念链：Datasets（数据集）→ Examples（样例）→ Experiments（实验）→ Evaluators（评估器）。工程化用法很朴素：攒 30–100 条真实场景样例，每次改提示词、换模型、动节点结构前先跑一遍实验，用同一数据集对拍新旧版本，抓住回归再上线；评估器既可打分也可断言（命中关键工具、输出包含必需字段）。针对多步骤 agent，官方还有「评估中间步骤」的专门指南——不只看最终答案，还看它选了什么工具、顺序对不对，这对 Graph 产品尤其重要：最终答案对、过程绕远路，意味着成本和延迟都在失控。

  • 调试顺序：先本地用固定输入单测每个节点，再整体跑图，最后才看 LangSmith 的轨迹。
  • 样例从哪来：真实工单脱敏后入库，失败案例优先收——它们最能区分新旧版本的差距。
  • 起步指标三件套：任务完成率、平均步骤数（成本与延迟的代理指标）、人工介入率；每个都按版本分别记录。
  • 每次实验记录版本号与变更原因，形成可回溯的迭代历史——这也是你向买家证明「模板在维护」的证据。

质量与安全：把注入面关小，把权限收到最小

买家问的是「它能干什么」，买家的安全团队问的是「它最多能干什么」。这一章讲三件事：认清工具层的注入面、把权限与数据边界设计到最小、用评测代替手感，最后给一份可以直接打勾的上架前自检清单。

🛡️

工具层的三种注入面：描述、输出、跨服务器

难度 ★★★适合：已写出第一个工具的你

工具和普通 API 最大的区别：返回值不进数据库，进的是模型上下文。网页正文、工单内容、第三方接口的字段、甚至别的工具的描述，都可能夹带「写给模型的指令」。OWASP 在 LLM 应用十大风险里把提示注入列为第一名（LLM01，2025 版），并且明确一点：恶意内容只要被模型解析就能生效，不需要对人类可见。你在第 9 章已经会封装 API 了，这一节专门处理封装之后新长出来的攻击面。

  • 工具描述投毒：安全公司 Invariant Labs 于 2025-04-01 披露 Tool Poisoning Attack——把指令藏进工具的 description，用户界面看不到、模型看得到。演示里一个加法工具 add(a, b, sidenote) 诱导模型读取本机 SSH 私钥，把内容塞进隐藏参数 sidenote 外传，而用户在确认弹窗里根本看不到这条参数。
  • 工具输出注入（间接提示注入）：你抓回来的网页、邮件、文档里带着指令，模型把它们当命令执行——比如「把会话内容发到某地址」。OWASP 对间接注入的定义就是：模型从外部内容里读到改变其行为的指令。
  • 跨服务器遮蔽与 rug pull：同一个客户端里，恶意服务器的描述可以覆盖可信工具的行为；服务器还可以先以干净描述过审、上架后再偷偷改掉。Invariant 给的对策是：界面区分「用户可见」与「模型可见」的指令、对工具包固定版本并做哈希校验、给跨服务器数据流加安全边界。

边界怎么画？MCP 官方 Tools 规范的 Security Considerations 一节给出最低要求：服务器必须（MUST）校验所有工具输入、实施访问控制、对调用限流、清洗工具输出；客户端应当（SHOULD）在把结果交给模型前先校验、对敏感操作请求人工确认、在调用前把入参展示给用户以防数据外传。落到你的工具上是三条铁律：返回最小集——只给模型完成任务需要的字段，其余用链接代替；截断要留痕——超长内容明确标注「已截断，共 N 条」，不要静默丢弃；密钥与 PII 永不出工具——先在服务端脱敏再返回。记住规范里的那句警告：工具注解（annotations）属于不可信数据，除非来自可信服务器。

💬 一线声音：「当恶意指令被嵌入 MCP 工具描述、对用户不可见而对 AI 模型可见时，工具投毒攻击就发生了。」——Invariant Labs《MCP Security Notification: Tool Poisoning Attacks》（2025-04-01），原文为英文，此处为转述翻译。
🔐

最小权限与人在回路：先问「它最多能干什么」

难度 ★★★适合：准备接入真实账号与数据的你

MCP 官方安全最佳实践把「范围最小化（Scope Minimization）」单独立节：先授予只含低风险读操作的最小初始范围，等真正触发高权限操作时再用授权挑战逐步提权。原文对宽范围令牌的代价用了直白的词：更大的爆炸半径（expanded blast radius）——一个泄露的 admin:* 令牌可以横向摸走所有数据，吊销时还要打断用户的全部工作流。对照到设计层面，可以逐条执行：

  • 读写分离：查询类与写入类拆成两个工具；写入类在描述里写明副作用，由客户端默认弹确认。规范对 Tools 一节的立场很明确：出于信任与安全，应始终有人在回路中，并有权拒绝工具调用。
  • 令牌最小 scope：每个工具拿到的凭据只够自己的用途、可随时吊销；不要让一个管理员全局令牌跑全部工具。
  • 危险动作先确认再执行：官方安全页对本地 MCP 服务器的建议是——执行前完整展示启动命令（含参数，不截断）、标记危险模式（sudo、rm -rf、外发网络请求、访问 SSH 密钥等敏感路径）、用沙箱和最小文件系统/网络权限运行。
  • 借用宿主的权限体系：以 Claude Code 为例，权限规则按 deny → ask → allow 顺序取第一条命中，并有 default / acceptEdits / plan 等模式可切换。把删除、外发、支付类工具放进 ask 或 deny，是零成本的兜底。

评测：改一行描述，也要重跑一遍

难度 ★★适合：所有准备上架的人

工具「好不好用」是可以测的。Anthropic 在 2026-01 的《Demystifying Evals for AI Agents》里给的最小起步门槛很低：20–50 个从真实失败里捞出来的任务用例就够开局，来源就是你的手工测试记录、bug 列表和用户反馈。评分器按「代码校验 + 模型评判 + 人工」三层组合，优先用确定性评分，只看结果、不看路径。还要区分 pass@k（k 次里成功一次即可）与 pass^k（k 次必须全部成功）——交互式工具看前者，自动化流水线看后者。如果一整套用例通过率是 0%，多半是任务描述写出了歧义，不是模型不行；原话是「任务说明里的歧义，会变成指标里的噪音」。

Anthropic 更早一篇《Writing Effective Tools for AI Agents》（2025-09）建议把评测做成循环：跑评测 → 读失败 transcript → 改工具描述 → 留出一组 held-out 用例防止「调到测试集上」。哪怕只改一行 description 也重跑一遍——那一篇的核心结论「对工具描述的小幅改动能带来显著提升」，反过来读同样是警告：小幅改动也能带来显著回退。评测集要有明确归属人，随着用户反馈持续往里加新用例。

上架前自检清单，每条都能打勾再提交：

  • 每个工具的 description 写清「何时用 / 何时不用」，参数名无歧义（user_id 而不是 user）。
  • inputSchema 覆盖所有入参校验；返回结构化内容时带 outputSchema。
  • 只读与写操作拆开，写操作默认需要用户确认。
  • 凭据最小 scope、可吊销，代码与文档里没有任何硬编码密钥。
  • 输出经过清洗：截断留痕、无密钥与 PII、长度有上限。
  • 可恢复错误用 isError: true 返回「发生了什么 + 怎么改参数」，让模型能自我纠正。
  • 限流与超时都已实现并有测试。
  • 审计日志覆盖每次调用。
  • 评测集不少于 20 例并纳入发布流程，描述改动即重跑。
  • 第三方依赖与安装脚本经过人工审读（供应链检查），依赖锁定了精确版本。

文档与试用：让陌生人 5 分钟跑通

买工具的人在下载之前只会花几十秒决定走不走。这一章把「陌生人 5 分钟跑通」拆成四件可以照做的事：README 的标准结构、免费额度怎么设计、失败信息怎么写、以及文档怎么替你挡住工单。

README：第一屏决定陌生人走不走

难度 ★适合：零基础

GitHub 官方对 README 的定位很朴素：告诉别人你的项目为什么有用、是做什么的、怎么上手。独立开发者常犯的错不是「没写」，而是第一屏全是徽章和架构图——陌生人要的是「这东西对我有什么用」和「最快多久能看到结果」。开发者文档圈把核心指标叫 time to first success：一个从没见过你项目的人，多久能拿到一次成功运行的结果。把所有结构决策都对齐到这个指标上：

  • 第一屏（约 15 秒）：一句话价值主张（给谁、解决什么）＋一个 30 秒能跑通的最小示例（代码块或 GIF）＋安装命令。徽章放第二行，别放第一行。
  • 快速开始（目标 5 分钟内）：先写前置条件（运行时版本、API key 在哪申请、哪些命令要全局安装），再给复制即可运行的命令，并给出预期输出——让用户能对照确认「我跑对了」。示例必须是可复制运行的真代码，不用伪代码，版本号钉死。
  • 排错区：列出 3–5 个最常见的失败信息与对应解法链接。你的第 13 章自检清单里的错误信息，都应该能在这里找到入口。
  • 下一步：进阶用法、完整文档链接、反馈渠道（issue 模板或群）。最后写清开源协议与免责声明。

  • 不要拿竞品密钥兜底：演示环境里塞自己的 key、限额严格，都比「引导用户改配置文件里的假 key」更体面，也更合规。

失败信息：写给新手，也写给模型

难度 ★★适合：所有上架者

可用性研究的经典结论（NN/g 可用性启发式第 9 条）是错误信息要帮用户识别、诊断、恢复，落到执行就是三问模板：发生了什么＋为什么＋下一步怎么办。NN/g 的两个具体警告值得贴在键盘边上：不要用 invalid、illegal 这类指责用户的措辞；不要过早报错打断探索性输入。另一句原话更狠——「最糟糕的错误信息，是那些根本不存在的错误信息」（静默失败比报错更毁信任）。

卖 AI 工具的你多了一类「用户」：模型本身。MCP 规范把可恢复错误设计成工具结果里的 isError: true，内容应当是「模型能用来自我纠正的可执行反馈」——也就是说，错误文本就是 Agent 用户读到的那份文档。给工具写错误信息时用这个模板：

  • 结构：[发生了什么] + [原因：参数 start_date 应为 ISO 格式日期] + [下一步：改为 2026-11-08 后重试；详见 docs/errors/E1201]。
  • 映射表：把上游错误翻译成你的错误——401 → 「key 无效或被吊销，去设置页重新生成」；429 → 「触发限流，等 X 秒重试」；上游超时 → 「服务端超时，已重试 1 次」。新手不需要知道上游是谁。
  • 分层展示：给人看的部分用自然语言，错误码和堆栈折叠进「详情」，方便用户贴给你的支持渠道。
💬 一线声音：「最糟糕的错误信息，是那些根本不存在的错误信息。」——Nielsen Norman Group《Error-Message Guidelines》（2023-05 更新），原文为英文，此处为转述翻译。

文档驱动的支持成本：把工单折进文档

难度 ★★适合：单人维护产品的你

独立开发者没有客服团队，文档就是你的客服。它不是一次性的发布材料，而是一条「工单→文档」的转化流水线：

  • 三振规则：同一个问题第三次出现在 issue 或私聊里，当天升级为文档条目——排错区就是这么长出来的。
  • 负反馈闭环：文档页放「本页有帮助吗」，点「否」必须留自由输入框；每条负反馈都指向一段没写清楚的内容。
  • 发版即改文档：changelog 与迁移说明和版本号同步发布，旧版本文档用路径归档，别让用户搜到过期答案。
  • 区分两类求助：状态页回答「是我在修」，排错区回答「是你的配置」——两类问题混在一个渠道里，你的支持时间会翻倍。

怎么判断文档合格？看工单的分布迁移：支持问题从「怎么装、怎么跑通」变成「怎么扩展、怎么接进自有流程」，说明快速开始部分已经完成使命——前一类问题的答案本该在 5 分钟跑通里就出现。

listing 优化：名字、描述、示例的三件套

难度 ★★适合：已经能跑、想被搜到的你
  • 名称可检索：市场搜索靠名称与描述匹配。名字里放用户会搜的词（产品＋动作），别玩谐音梗。MCP 规范对工具名的建议是 1–128 字符、只含字母数字下划线连字符和点——工具名克制，listing 名称可以更自然。
  • 描述写「何时用」：审核员和模型都要读你的描述。一段合格描述 = 给谁用＋解决什么＋何时不要用它（避免误调用），与第 13 章的 description 写法同源。
  • 图标与截图规格对齐：Cline 明确要求 400×400 PNG；OpenAI 目录收录会检查图片资产。准备一套规格统一的图标，别在每个市场重复返工。
  • 示例先行：listing 页的示例就是你的第一屏——复制即可运行的一条命令＋一段预期输出，直接从第 14 章的快速开始搬。
  • 让安装命令无处不在：skills.sh 按安装量排名，安装命令出现在 README 第一屏、X 简介和文档页眉，每一次复制都是榜单投票。

被拒的常见原因，与上架后的数据面板

难度 ★★★适合：被拒后寻找原因的你

被拒大多不是玄学，而是能对号入座的材料问题：

  • 校验失败：marketplace.json 的 JSON 语法错误、必填字段缺失、命名规则违规、相对路径包含 ..——这些 claude plugin validate 都能在提交前抓出来；官方强调「校验和安装抓到的问题不一样」，两个都要跑。
  • 名称不一致：marketplace 条目名与 plugin.json 的 name 不同，按 manifest 名安装直接失败。
  • 材料缺项：Cline 的 400×400 图标、OpenAI 的审核材料与测试用例、listing 图片规格不合规。
  • 自测确认没做：Cline 要求「只给 README 也能装成功」——你贴在 issue 里的安装说明要能被 Agent 逐字执行。
  • 命名空间验证失败：MCP 注册表要求你证明拥有该 GitHub 账号或域名，验证不过无法发布。
  • 敏感领域额外审查：加密货币相关工具在 Cline 会被要求额外验证；任何市场都更严格对待高权限工具（支付、文件系统、外发数据）。

数据面板的真相：截至 2026-11-08，五大市场里只有 skills.sh 的榜单是公开的安装遥测；MCP 注册表只收元数据、不公布安装量；Cline、Anthropic 目录与 OpenAI 插件的曝光/安装数据暂无公开口径（以上均以各市场当期页面为准）。所以独立开发者的做法是自建遥测：安装命令的埋点、GitHub star/issue 曲线、自家 dashboard，再用固定节奏发版——每周 changelog、双周小版本、每月一次大更新，每次发版都是一次回到曝光池的机会（衔接第 28 章的 90 天计划）。

X 与 CT：宣发的排期表

从星标到付费：设计你自己的漏斗

计量收费落地：把每次调用变成一笔能对账的收入

按 token 计费的产品，收入和成本都随用量浮动。计量收费的难点不在定价（配比实验见第 21 章），而在工程：把每次调用可靠地记下来、算清楚、收得上钱、防得住滥用。本章给计量系统的最小实现、三条收款路径的取舍、免费层的切法，以及最容易被忽略的一笔账——客服成本。

🧮

计量系统最小实现：一次调用如何变成一条账

难度 ★★★适合：产品已有调用量

计量的本质是一张「用量事件表」：谁（用户或 API key）、何时、计量项（输入/输出 token、请求数、成功任务数）、数量。新手最容易犯的错是自己数 token——主流模型 API 的每次响应都自带 usage 字段（输入/输出分列），在网关层原样落库即可，别重新发明分词器。四条工程底线：

  • 幂等：每条事件带唯一 request_id，客户端重试或你重放消息队列时不能重复计费——这是账单争议的头号来源。
  • 出账走现成管道：官方流程是给订阅挂一个计量价格（metered price），账期内调用用量记录 API 逐笔上报，期末由支付平台按求和等聚合规则自动出账（Stripe 官方文档口径，检索 2026-11-08）。你只负责「记账」，不负责「算钱」。
  • 配额先软后硬：限流用令牌桶或滑动窗口；超限时返回 429 并带 Retry-After 头，先给提醒和升级链接，再拒单。突然掐断付费用户比宕机更伤口碑。
  • 防滥用三层：注册端做邮箱/手机验证和人机校验（如 Cloudflare Turnstile 类方案）；配额端按 key 限额而不是按 IP；账务端设单用户单日消费上限和异常用量告警。免费层滥用最常见的形式是多账号薅配额，提高注册成本比事后追讨便宜。
💬 一线声音：转售模型能力之前先算清自己的单位成本——Anthropic 官方成本文档给 Claude Code 的口径是「平均每位开发者每个活跃日约 $13，每月 $150–250，90% 的用户低于每天 $30」（code.claude.com/docs/en/costs，检索 2026-11-08）。你的售价减去这条线，才是真实毛利空间。

免费层怎么切，客服成本怎么算

难度 ★★适合：上线前做最后设计

免费层是获客预算，不是慈善。行业基准是免费转付费只有 2%–5%（Lenny's Newsletter 与 KISSmetrics 汇总口径），所以免费层的预算上限 ≈ 预期付费收入 × 转化率的倒数。三种切法按顺序试：

  • 按价值指标限配额：限「成功任务数」或「1k 次调用」，不限「导出 PDF」这类小功能——用量触顶那一刻就是最好的升级推销时机。
  • 免费版带署名传播：生成的报告、机器人主页带「Powered by 你的产品」链接，让免费用户替你获客。
  • 用「限时长试用」代替永久免费验证付费意愿：工具类买家带着明确任务来，转化判断更准（第 21 章有详细配比实验）。

客服是计量收费的隐藏成本。行业基准（ScreenMeet 汇总 HDI/MetricNet 数据，检索 2026-11-08）：电话均值 $17.19/票、邮件 $16.13、聊天 $15.72，SaaS 行业常见 $25–35/票。计量收费特有的一类客诉是账单争议——「这批调用是谁发起的？」对策在系统设计里就埋好：每次调用留可查审计日志，账单页支持逐条明细导出，退款政策写在定价页而不是退款邮件里。AI 客服先挡一层常见问题（配额、发票、升级），人工只接账单争议和故障，才能把综合单票成本压住。把「每 100 个付费用户预计产生多少张工单 × 单票成本」列进定价模型，很多产品的「伪毛利」就露出来了。

💬 一线声音：限流实践社区的共识是「限流的目的是公平而不是惩罚」：给出清晰的 429 错误与 Retry-After、按 key 而非按 IP 限额、对突发流量用突发窗口——Zuplo《API 限流十条最佳实践》（2026，检索 2026-11-08）把「可预期的限流」列为付费 API 的信任基础。

B2B 定制：私有 MCP 与企业 Agent 的报价与交付

企业不为「AI」付费，为可验收的业务结果付费。B2B 定制和个人产品的区别不在技术，而在采购流程：有人立项、有人管安全、有人压价、有人验收。本章拆企业需求的三种形态、两条获客路径、三种部署位形对应的合规要点，以及「开发费＋维护费＋许可费」的报价结构。

🏢

企业要什么，从哪找到他们

难度 ★★★适合：有 2 个可讲案例的你

2026 年企业 AI 定制需求集中在三种形态，复杂度和客单价依次升高：内部知识问答（RAG 接文档库，几周级项目）、流程自动化 Agent（对接 ERP/CRM 执行动作，季度级项目）、私有 MCP 服务器（把内部系统按标准协议安全接进员工的 AI 客户端，常与两者叠加）。私有 MCP 是 2025–2026 年长出来的新需求位：MCP 协议由 Anthropic 于 2024 年 11 月开源，2025 年 9 月 8 日官方注册表（Registry）进入 preview——官方博客对它的定义是「一个面向公开 MCP 服务器的开放目录和 API」，并明确它可作为企业自建子注册表的上游。给企业交付私有 MCP 时，「发布到官方注册表」或「部署企业子注册表」都是可以写进方案的标准选项。

获客渠道按转化率排序：官方伙伴目录是生态内的正规入口——Anthropic 的 Claude Partner Network 提供可公开检索的认证伙伴目录（partnerhub.claude.com/directory），OpenAI 也维护着覆盖战略、部署、集成、采纳四类的 Partner Network 页面；进目录需要案例与认证门槛，适合已有交付记录的团队。熟人转介绍与行业社群仍是独立开发者的主渠道——企业采购信「同类企业用过」，一个可核实的案例胜过十页方案。内容获客是把 POC 过程写成复盘长文：企业买家搜「我们行业＋RAG/Agent 怎么落地」时，复盘文就是你的销售前置。冷启动期的正确姿势：用一个小型 POC（固定价、两至四周、带验收标准）换案例授权，而不是先花三个月做官网。

💬 一线声音：MCP 官方「企业托管授权」扩展文档的原话（转译）：「不是让每个员工各自授权每个 MCP 服务器，而是由组织的 IT/安全团队在一处集中管理访问策略。」——这句话就是企业买家心里「私有 MCP」该长什么样的答案：接他们已有的身份系统，而不是发明新的账号体系（modelcontextprotocol.io，检索 2026-11-08）。

报价结构与交付验收：开发费、维护费、许可费

难度 ★★★适合：第一次写合同的你

B2B 定制的报价三件套：开发费——范围明确选固定价（fixed price），需求会漂移选工时物料制（T&M），这是软件外包的两种基础合同形态，也可以组合使用；维护费——行业惯例是每年收取初始许可费或开发成本的一个固定比例；许可费——按席位或按实例计价的软件使用权，区别于一次性开发费，是持续收入。此外还有第四种常用形态 Retainer（预聘用金）：客户按月预付，买断你一部分工时容量，常见周期六到十二个月。公开基准显示（检索 2026-11-08）：大型软件厂商年维护费约为许可费的 18%–22%（VendorBenchmark 词汇表：Oracle 约 22%、SAP 约 19%、IBM 20–25%）；自研定制软件的年度维护预算惯例为初始开发成本的 15%–20%（Timeline 口径）——这就是你报维护费的锚。

个人智能体变现：把 Agent 做成订阅产品

个人智能体不是「更小的企业 Agent」——它的买家是「自己」，付费意愿来自省下的时间，留存来自使用习惯，而最大的转化杠杆和最大的翻车点都是同一件事：数据隐私。本章拆三种产品形态与平台挤压、订阅制设计与留存基准，以及隐私为什么值得当成第一卖点来定价。

🤖

三种产品形态，与平台原生功能的挤压

难度 ★★适合：正在选题的你

个人智能体目前跑通订阅的形态有三类，留存逻辑各不相同：个人助理（对话＋记忆＋代办，高频但易被大平台通用助手挤压）、监控播报（盯价格/舆情/到货/账单，定时跑、主动推送——「沉默期长」但用户离不开）、数据整理（发票、简历、聊天记录、订阅服务的结构化归档，项目制使用，适合配模板复购）。做之前先看平台把「通用部分」做到哪了：

数据隐私：第一卖点，也是第一风险

难度 ★★★★适合：产品要碰个人数据的你

个人智能体要读邮箱、账单、日程、聊天记录——你握有的敏感度超过大多数 SaaS。反面教材是微软 Recall：2024 年发布即被安全研究者批为「隐私噩梦」（核心批评是未加密的本地截图数据库），随后撤回延期；2024 年 9 月 27 日微软官方博客公布重做的架构——改为默认 opt-in、访问需 Windows Hello 验证、默认过滤敏感内容（密码、证件号、卡号）、本地数据库加密；2025 年 4 月独立安全研究者实测后仍提出新的担忧。一次隐私事故的代价是数月返工加长期的信任伤痕。正面样本是 Proton 的 Lumo：把「不记录对话、不拿你的数据训练」做成核心卖点，并据此定价（免费档之外 Plus $12.99/月）——隐私是可以摆上价签的。

落地为一份你自己产品就能用的清单：

  • 明示：收集什么、存多久、给哪个模型提供商，写在第一次授权弹窗里而不是隐私政策第 14 条。
  • 最小化：监控播报只回传「事件发生」的结论，能不回传原文就不回传；本地能算的不上云。
  • 可退出：一键导出＋彻底删除；删号时连记忆与向量索引一起删。
  • 默认过滤：密码、证件号、卡号在入库前脱敏——Recall 的整改项就是你的及格线。
  • 按法域合规：用户在欧盟走 GDPR 口径，在中国大陆遵循《个人信息保护法》的最小必要与单独同意要求。

定价实验：免费、付费与开源的配比

定价不是拍脑袋定的一个数字，而是一次可以反复修改的实验：先决定「免费给什么」，再设计版本分层和锚点，然后用数据一小步一小步地调。本章给你三种经过验证的免费/付费切分方式、一套锚点设计原则，和低流量也能跑的迭代方法。

免费从哪来：三种切分模式

难度 ★★适合：零基础

「免费」不是慈善，它是获客成本的一种支付方式。三种主流切法各有适用场景，选错模式是新手最常见的亏损起点：

  • Freemium（免费增值）：完整或接近完整的产品永久免费，用配额（人数、请求数、存储）划出付费线。行业共识是免费用户转付费率只有 2%–5%，这不是失败信号，而是这个模式的正常水位——它的价值在于获客几乎零门槛。
  • Open-core（开放核心）：核心代码开源可自托管，付费的是托管服务和企业功能。GitLab 是教科书案例：其官网定价页显示，Free 档对私密顶层群组限制 5 个用户、400 计算分钟/月、10 GiB 存储，Premium 档 $29/用户/月（年付），Ultimate 走定制报价（检索日期 2026-11-08）。
  • 免费试用：全功能限时开放。Plausible Analytics 给 30 天试用、无需信用卡，试用期间直接开放全部 Business 档功能——它没有免费档，开源只是自托管选项，托管的 SaaS 版从 Starter $9/月起（按 10k 月页面浏览量的入门档）。

价格锚点与版本分层：让「中档」成为默认答案

难度 ★★★适合：已有免费用户

锚定效应和诱饵效应是两件不同的事，别混用。锚定是先展示高价档，让中档显得便宜；诱饵是在你的目标档旁边放一个「明显不划算」的选项，把选择推回目标档。PayPro Global 的定价页指南明确建议把最高档放在显眼位置作为锚点；Figma 的定价页设计指南则强调用「Most popular」徽章和视觉层级引导注意力。

  • 三档结构是安全起点：低档降低启动门槛、中档放「推荐」徽章、高档做锚点。Plausible 的 Starter $9 / Growth $14 / Business $19（10k 页面浏览量入门档）就是干净的三档加一档定制。
  • 诱饵必须是「真的值那个价但不合适」：例如一个只差一项关键功能的档位，而不是随便编的价格。虚假诱饵被识破一次，整张定价页的信任就没了。
  • 分层维度要匹配买家的成长路径：工具类产品用「用量」（页面浏览量、API 调用数、计算分钟）比用「席位数」更贴合个人开发者的预算曲线——Plausible 明确写「按页面浏览量计价，不按席位」；GitLab 用「用户数 + 计算分钟」双维度，适配团队规模化。
  • 给慈善与开源友好用户一个折扣口：Plausible 给非营利组织、教育机构、开源项目 15% 折扣（仅年付 Business 档）。这是低成本的品牌投资，也是积累案例的渠道。

用量分层的另一面是「超量恐惧」，Plausible 的处理值得抄：单月偶发超量不收费、不断服务，连续两个月超量才提示升级——先把超量焦虑从买家脑子里拿掉，转化阻力会小很多。

用数据迭代定价 + 调价怎么沟通

难度 ★★★★适合：已有付费用户

定价迭代最反直觉的一条：经典 A/B 测试对小流量产品基本不可行。以 5% 基线转化率估算，每个变体需要约 1,000 个转化才能得到统计显著的结果——月转化几十单的独立产品要等几年。可行做法是改成「顺序实验」：

  • 季度节奏改一次，只改一个变量：只动价格、只动分层边界、或只动锚点排布。Price Intelligently 的公开结论（经 Paddle 引用）是：按季度迭代定价的公司增速约为年度迭代者的 2–3 倍。
  • 盯三个护栏指标：ARPU（每用户平均收入）、升级率、流失率。涨价时流失率小幅上升但 ARPU 涨幅更大就是净赢；降价带来大量低价值用户挤占支持时间就是净输（第 22 章会把支持时间算进账本）。
  • 流量不够就用访谈代替实验：直接问 10 个目标用户「这个价你觉得贵/便宜/贵得离谱吗」（Van Westendorp 四问法），独立开发者访谈一轮的收益常常大于半年的 A/B 等待。

调价沟通的三个硬规则：提前 30–90 天通知（多来源建议 45–60 天最佳）；邮件里写清「现在付多少、以后付多少、哪天生效」三件事；给老用户祖父条款（grandfathering）——锁定旧价 6–12 个月、或对新价永久豁免。Orb 的调价指南强调把涨价和已交付的新价值绑定叙述，而不是只发一张新账单。

把你的时间算成钱，再谈砍留

难度 ★★★适合：所有阶段

一人公司的账本里最贵的一行经常没被记录：你自己的时间。方法很朴素——给自己定一个「影子时薪」，用它折算所有维护、支持、营销时间：

  • 定影子时薪：以你接单/受雇的市场价为锚（比如 ¥200–400/小时，自定）。它不是成本科目，是机会成本科目：花在 A 产品上的 10 小时，就是 B 产品少赚的 10 小时。
  • 每月记两类时间：维护时间（依赖升级、报错修复）和支持时间（答疑、退款、工单）。前者决定产品的「息屏成本」，后者乘以影子时薪直接进成本表。
  • 算术示例（数字为方法演示，非公开统计）：$9/月产品，月 30 个付费用户 = $270 收入；通道费按 10.6% 约 $29；支持每月 5 小时 × ¥300 ≈ $210；托管 $5——毛利所剩无几，而你的 5 小时还没算修复一个突发 bug 的 3 小时。这类产品要么涨价、要么做成零人工（文档 + 自动化）。

砍留决策建议按季度跑一遍，标准尽量客观：

  • 砍：毛利为负且加价/限配额后用户强烈流失；影子时薪折算后月亏扩大；你已连续两个季度不想碰它。
  • 留：毛利薄但稳定盈利且几乎零维护（息屏型现金牛）；或它是主产品的获客入口（免费开源档的价值在第 21 章已算过）。
  • 怎么砍才不伤口碑：提前公告（参考第 21 章调价沟通的三件套）、给出数据导出口、老用户折扣迁移到主线产品、保留归档仓库。删库式关停是独立开发者口碑的头号自杀行为。

自有渠道：官网与邮件列表，第一天就开始建

难度 ★★★适合：所有阶段

对冲平台风险最便宜的手段，是把「观众」变成「联系人」：一个自己的官网 + 一份邮件列表。邮件是直达渠道，没有算法插队，用户换平台你的联系还在——这是多数邮件营销平台（Kit、beehiiv、MailerLite 等）的共同卖点，也是被反复验证的共识：你拥有名单，平台只拥有流量。

  • 建多早？从第一个可下载的铲子开始。上架页放订阅框、README 里放官网链接、交付邮件里加一条「订阅更新」。早期 100 个邮箱的价值远超 10,000 个平台粉丝。
  • 成本量级：邮件服务小流量档普遍免费或每月几十美元；真正的成本是每周一封「更新 + 干货」的写作时间（按第 22 章影子时薪记账）。
  • 对冲动作清单：官网列出所有平台的入口（哪个平台封禁你，用户仍找得到你）；文档自托管（GitHub Pages 级别即可）；关键客户加微信/邮件双通道；每个平台的数据（用户联系方式、发票记录）每季度导出一次存档。

知识产权与开源：协议选择与抄袭应对

协议不是法律文书爱好者的装饰品，它直接决定你的铲子能不能收到钱、被抄袭时你手里有什么牌。本章讲清 MIT/Apache/AGPL 对商业模式的实际差别、双许可怎么收商业授权费、被抄了怎么一步步取证维权，以及用协议设计收入的思路。本章不构成法律意见，重大决策请咨询执业律师。

📜

三大协议对生意的影响：MIT、Apache-2.0、AGPL-3.0

难度 ★★适合：零基础

选协议前先回答一个问题：你希望陌生人拿你的代码做什么？GitHub 官方的 choosealicense.com 对 MIT 的描述是「简短直接，几乎允许任何人以任何方式使用你的项目」，包括做闭源发行版，Rails、Babel、.NET 都在用它。这很适合「求扩散」的工具；但如果你靠托管版或高级功能收费，就要考虑带条件的协议：

维度MITApache-2.0AGPL-3.0
能否闭源商用能，保留版权与许可声明即可能，保留版权与 NOTICE 文件能，但受网络条款约束（见下）
专利无显式条款贡献者显式授予专利许可，含专利报复条款（起诉专利侵权即终止授权）属 GPLv3 体系，含专利相关条款
修改后分发要不要开源不用不用（需标注修改）分发需以同协议开源
修改后做云服务（SaaS）无开源义务无开源义务须向通过网络交互的用户提供对应源码（第 13 条）
典型用途求最大扩散的库与小工具预期企业贡献、担心专利纠纷的项目靠托管/服务收费的商业开源产品

关键差别在最后一行：GPL 的「分发才触发开源义务」留了一个著名的 SaaS 漏洞——云厂商把改过的软件只放在自己服务器上，从不「分发」，就可以不交源码。AGPLv3 第 13 条（远程网络交互）就是为了堵这个洞：GNU 官方文本要求，修改版的程序必须向所有通过网络与之交互的用户提供获取对应源码的途径。对卖托管服务的一方，这是护城河；对只想「用一下」的企业，这是合规顾虑——两种立场共同决定了协议的选择。

  • MIT 的代价：任何人（包括云厂商）都可以拿去闭源商用，你不欠他们源码，他们也不欠你任何东西。适合以「被集成」为目标的组件。
  • Apache-2.0 的价值：企业法务最熟悉的「安全选项」，显式专利授权让贡献者和使用者双方都不用自行推断专利地位。
  • AGPL 的双刃：对商业开源者是收入保护，对采用者是合规成本——很多公司内部直接禁用 AGPL 组件，选型前想清楚你站在哪一边。

双许可与商业授权：同一份代码，两种价签

难度 ★★★★适合：有企业客户

双许可（dual licensing）是把同一个代码库同时放在两个协议下：开源版用强 copyleft（如 GPL/AGPL），商业版卖「豁免 copyleft 义务」的商业授权。OSI 的科普页把它与 open-core 明确区分：open-core 是两套不同的代码（社区版 + 付费版各一部分），双许可是同一套代码、两份协议。MySQL 和 Qt 是最著名的实践者——Qt 至今同时提供商业许可与开源许可（GPL/LGPL）。

  • 前提是版权集中：只有版权所有者能卖商业授权。所以双许可项目一律要求外部贡献者签 CLA（贡献者许可协议），把贡献的版权/再许可权交给你。没有 CLA 的仓库做不了双许可，因为每一行外来代码的作者都有权主张自己的许可。
  • 收入来自 copyleft 的摩擦：能遵守 AGPL 的用户免费使用；被 AGPL 合规成本（或开源自己代码的顾虑）卡住的企业，就是商业授权的买家。摩擦越大，付费意愿越明确。
  • 独立开发者的轻量版：不必做严格双许可，常见替代是「AGPL 开源核心 + 商业授权卖多租户/白标/企业功能」，或直接采用 open-core（参考第 21 章 GitLab、Plausible 的分层定价）。
  • 写清楚授权范围：商业授权合同要写明允许的部署数量、可否去除版权标识、是否含更新与支持，避免「卖一次、被当无限授权用」。

issue 治理与支持分级：把答疑从仓库里分流出去

难度 ★★适合：零基础

支持成本失控的第一原因，是把「答疑」和「缺陷」混在同一个 issue 列表里。成熟开源项目的解法是分诊（triage）：新 issue 先打标、归类、分优先级，再决定谁花时间。Traefik 项目在官方贡献者指南里公开了整套流程：新 issue 自动打上 status/0-needs-triage 标签，分诊时按「优先级/严重度、归属、类型」三维分类；提问类直接打 kind/question 转文档或社区论坛后关闭；疑似缺陷先搜重复、再尝试复现，可复现的升级为 kind/bug/confirmed 并定优先级；缺信息的打 contributor/waiting-for-feedback，60 天无回复自动关闭，提问类 8 天无动静自动关闭（来源：Traefik 官方分诊指南，检索日期 2026-11-08）。抄它的骨架：

文档驱动：让文档替你值一次班

难度 ★适合：零基础

第 14 章讲过怎么写文档，这里讲怎么用文档减少支持。方法只有三步：① 把最近一个月收到的重复问题排个序，取前三名；② 每个问题写一节带完整命令的文档（能复制粘贴直接跑通的程度）；③ 在 issue 模板里放一个勾选框「我已读过对应文档链接」。社区经验是，写文档一小时，通常能挡掉此后每周数封重复邮件——按第 22 章的影子时薪折算，这笔投入一个月内回本。

  • 给 AI 读的文档是新支持面：2025 年以来，「LLM-first documentation」开始流行——用户先问 AI 而不是先开 issue，AI 引用你的官方文档作答，重复工单显著减少。把文档做成机器友好格式（结构化 Markdown、llms.txt、AGENTS.md），等于给 AI 客服发了工牌。
  • 文档报错等于补文档：每次支持对话结束时，花两分钟把这次问答浓缩进 FAQ，支持量才会单调递减而不是恒定循环。

依赖升级与破坏性变更：小步、定时、按序

难度 ★★★适合：所有阶段

依赖积压三个月不升，升级就从「家务」变成「手术」。Renovate 官方的升级最佳实践给出了一套可直接照抄的节奏（来源：docs.renovatebot.com，检索日期 2026-11-08）：

  • 勤升小步：更新越频繁，单次 PR 越小、越容易评审，出 CVE 时你才有余力立刻合并补丁；锁文件按周维护即可。
  • 延迟自动合并：对第三方依赖设置 minimumReleaseAge = 14 天再自动合并，给注册表留出撤下恶意包的时间窗——这是供应链攻击的现实防线。
  • 大版本按序爬：1→2→3→4 逐级升，绝不直接 1→4；每个大版本一个独立 PR，先读变更日志再动手。合并出问题就回滚到已知好版本，改天再试。
  • 修流程不怪人：Renovate 团队强调，逃避升级的根因通常是「构建太慢、测试缺失、发布靠手动」——把 CI 提速、让关键路径每个 PR 都跑测试，升级阻力自然消失。

反过来，你对自己的用户也有破坏性变更义务：给参数重命名、删默认值、换配置文件格式这类动作，走「公告 → 弃用期兼容 → 主版本发布 → 迁移指南」四步。一人项目的最小可行节奏是：破坏性变更只跟主版本走，弃用期至少留一个完整的次版本周期，README 顶部挂迁移说明。这既是第 24 章开源协议之外的「社区契约」，也是第 23 章平台依赖的减震器——你的用户迁移成本越低，你对单一平台的谈判地位越稳。

💬 一线声音：Renovate 官方文档的原话是「Fix the process, not the people」——把流程、规则和习惯修好，而不是责怪不想升级的开发者（来源：Renovate 升级最佳实践文档，检索日期 2026-11-08）。

升级信号自测：用户在替你举手

难度 ★★适合：有开源工具

托管带来的成本与责任变化

难度 ★★★适合：准备上云

上云之后，你的身份从「发代码的人」变成「跑系统的人」，新增四类长期责任，第 22 章的成本表要相应加行：

  • 可用性预期：自托管宕机是用户自己的事；云版宕机是你的事。至少准备：健康检查 + 崩溃告警 + 一页「状态页」话术。一人公司不建议承诺 SLA 百分比，用「尽力而为 + 状态页」诚实表述。
  • 数据责任：你替用户存数据，就要对备份、恢复、泄露负责。Pro 档的 7 天每日备份是底线配置；隐私政策与数据处理说明在收款前写完（第 13 章安全清单的延伸）。
  • 支持边界：学 Plausible 的分层——付费云用户获得「开箱即用」的排障支持；自托管用户回到社区互助，不承诺逐个排障。边界不写清楚，双轨支持会拖死你。
  • 发布节奏双轨制：Plausible 的实践是云版每日更新（自己运维、随时可回滚），自托管版半年一次「长期支持」节奏（先在云端跑稳再放给无法快速升级的用户）。一套代码、两条节奏，别让最慢的用户拖住你。
  • 协议升级：Plausible 从 MIT 换成 AGPL，理由是防止云厂商拿它的代码做竞争性托管服务而不回馈——如果你打算走这条路，第 24 章的协议选择要在上云之前定好。

AI 类工具上云还有一条独有的责任：API 成本。第 22 章的数据（重度用户 p99 每月可烧 $30+）意味着云版必须内置配额、限速与异常用量告警，托管一个「无限量」的 AI 工具等于给自己埋雷。

AI 原生分发：让 Agent 主动找到你的工具

传统分发是把页面排在人类搜索结果的前面；AI 原生分发是让你的工具成为 Agent 在规划任务时直接调用的选项。这一章是本手册的独有视角：你的 SKILL.md 描述字段、注册表元数据和模型训练数据里的可见性，共同决定了 Agent 会不会找到你。它与姊妹篇《AI 流量手册》的 GEO 打法互补——那本书讲被答案引用，本章讲被调用触发。

被「引用并调用」的优化方向：给模型递证据

难度 ★★★适合：已上架

学术研究已经给「如何被生成式引擎选中」打了样。GEO（Generative Engine Optimization）论文在生成式搜索场景跑了大规模查询基准，结论是优化手段最高能把内容可见性提升 40%，其中引用来源、引用原话、给出统计数字是有效策略（来源：arXiv 2311.09735，ACM SIGKDD 2024，检索日期 2026-11-08）。把这套结论翻译到「被调用」场景：

  • description 写「能做什么 + 什么时候用」：OpenAI 官方文档给的对照示例是「Review and redline vendor agreements using the fallback clauses」优于空泛的「Helps with legal work」——模型靠具体动词和场景词做匹配，形容词帮不上忙。
  • 命名走规范：MCP 服务器用反向 DNS 命名空间（io.github.用户名/kebab-case 名），技能名与目录名保持一致且少用缩写——模型对规范命名的置信度更高。
  • 文档可被机器直接读：llms.txt 是放在网站根目录的结构化 Markdown 清单（Jeremy Howard 提出的自愿性提案，非官方标准）；Anthropic、Vercel、Cloudflare 等开发者产品的文档站已采用，Google 明确它不影响搜索排名，但 2026 年 5 月起 Chrome Lighthouse 新增「Agentic Browsing」审计类别，把 llms.txt 就绪度作为 Agent 就绪信号纳入（来源：Firecrawl 指南，检索日期 2026-11-08）。你的工具站加一个 llms.txt，成本十分钟。
  • 证据链三件套：README 与 description 里写可验证的数字（测试覆盖、跑通的平台版本号、基准对比），配一条最小复现命令——模型和人类一样，更信任能核对的东西。这也是 GEO 论文「统计数字有效」结论在工具分发上的直接应用。

与姊妹篇《AI 流量手册》的分工：GEO 打法解决「被答案引用」——你的教程、对比页、文档被 AI 搜索引用为出处，带来人类访客；本章的注册表与 description 优化解决「被调用触发」——Agent 在执行任务时直接选中你的工具。两条线共用同一份底层资产：结构化、可验证、机器可读的产品信息。做完第 16 章的冷启动后，把「AI 能不能独立找到并正确调用你的工具」加入每周检查清单——这是上一代分发完全不存在的增量渠道。

先管理预期：Indie Hackers 社区的公开帖子里，有开发者回忆自己的工具上架 6 个月才收到第一笔收入，另一条高赞帖的标题直接写着「达到 $1k MRR 需要 5 个月」——这些是社区体感而非抽样统计，但方向一致：90 天拿到首笔收入是乐观但可达的目标，市场线分成收入常常更慢。这正是三条线并行的原因：定制与服务的现金流垫底，让你等得起市场线的复利。

💬 一线声音：CB Insights 对 2023 年以来 431 家公开关停公司的分析写道：「资金耗尽以 70% 高居榜首，但它几乎总是死亡的终因，而不是根本问题」——真正的根因是产品错配市场（43%）。落到 90 天计划里就是：收入没来先查「有没有买家」，再查「渠道断在哪」，最后才改产品（来源：CB Insights，检索日期 2026-11-08）。

第 12 周的决策规则提前写好，避免临场情绪化：

  • W10 结束仍 0 收入：先查渠道漏斗（曝光有了但没有点击 → 文案问题；有点击没有安装 → 落地页或 description 问题；有安装没有付费 → 定价或价值问题），只改断掉的那一环。
  • W12 有真实用户但 0 收入：不是砍，是换模型——按第 21 章把免费档改成「免费 + 付费省事档」，或按降级链把工具包装成定制服务，让定制现金流反过来养产品。
  • 有收入但毛利为负：回第 22 章砍变量——限 AI 用量、换支付通道、涨价一档，先动成本再动价格。
  • 连续两季不想碰它：触发第 25 章退出评估，体面归档，带着 README、文档和候补名单开下一个项目——这些资产 90 天里都没白做。

最后提醒一条纪律：90 天计划最容易死于「加需求」。任何不在每周产出物表上的想法，记进 backlog，W12 决策时统一处理——第 28 周的你，会感谢第 3 周忍住没有重构的你。
